# @contextos-ai/database

Single source of truth for the database: Prisma schema, generated client, and the singleton accessor every app shares.

## Why this package

- **One schema** — `prisma/schema.prisma` is the only place models are defined. No drift across apps.
- **One client** — apps import `prisma` from here; never instantiate `PrismaClient` directly.
- **One migration history** — `prisma/migrations/` is the canonical record. Apps cannot diverge.
- **Database boundary** — if the ORM ever changes (Drizzle, Kysely, raw SQL), only this package changes.

## Structure

```
packages/database/
├── prisma/
│   ├── schema.prisma           ← models, datasource, generator
│   └── migrations/             ← generated by `prisma migrate dev` (committed)
└── src/
    ├── index.ts                ← re-exports prisma + Prisma types
    └── client.ts               ← singleton (cached on globalThis in dev)
```

## Consumption

```ts
// Anywhere in apps/api or apps/web (Server Components, Route Handlers, etc.)
import { prisma, type User } from "@contextos-ai/database";

const user = await prisma.user.findUnique({ where: { id } });
```

The singleton pattern means:

- **Dev**: HMR reuses one client; no connection-pool exhaustion
- **Prod**: process gets one fresh client at boot

## Scripts (run from repo root or inside this package)

| Command            | What it does                                                           |
| ------------------ | ---------------------------------------------------------------------- |
| `pnpm db:generate` | Regenerate the Prisma client (after schema edits)                      |
| `pnpm db:migrate`  | Create + apply a new migration in development                          |
| `pnpm db:push`     | Push schema to DB without creating migrations (rapid prototyping only) |
| `pnpm db:studio`   | Open Prisma Studio (DB browser)                                        |
| `pnpm db:deploy`   | Apply migrations in production (no schema changes)                     |
| `pnpm db:reset`    | Drop DB, re-run all migrations, re-seed (destructive — dev only)       |
| `pnpm db:seed`     | Run `prisma/seed.ts` (added later)                                     |

All DB commands load env vars from root `.env.local` then `.env` via `dotenv-cli` — single source of truth for `DATABASE_URL`.

## Environment

Set `DATABASE_URL` in the **root** `.env.local` (gitignored). Format:

```
DATABASE_URL="postgresql://user:password@host:5432/dbname?schema=public"
```

The schema's `datasource db { url = env("DATABASE_URL") }` reads from `process.env`. `dotenv-cli` loads root env files before invoking the Prisma CLI.

## Adding a model

1. Add the model to `prisma/schema.prisma`
2. Run `pnpm db:migrate` (prompts for migration name)
3. Verify generated SQL in `prisma/migrations/<timestamp>_<name>/migration.sql`
4. Commit both `schema.prisma` and the new migration directory
5. The Prisma client regenerates automatically — the new model is typed in apps immediately

## Conventions (all enforced in the current schema)

- **IDs**: `cuid()` — sortable-ish, URL-safe, collision-resistant
- **Timestamps**: `createdAt` + `updatedAt` on every model
- **Soft delete**: `deletedAt DateTime?` — queries should filter `WHERE deletedAt IS NULL`
- **Table names**: plural snake_case via `@@map("users")` (decouples DB names from Prisma model names)
- **Indexes**: add up-front on common query fields; vastly cheaper than backfilling later
- **Cascading deletes**: explicit `onDelete: Cascade` on dependent relations (auth sessions, etc.)

## Why we don't have richer domain models yet

This package is **infrastructure**. Domain models (`Conversation`, `Message`, `ApiKey`, `Organization`, etc.) come with the product features that need them. Adding them here speculatively would either:

1. Force a backfill rename when product specs land, or
2. Get committed unused and rot.

Start with `User` + `Session` (every SaaS needs them), grow from there.
